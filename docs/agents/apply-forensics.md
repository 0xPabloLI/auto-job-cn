# 投递取证与跳岗台账

> 什么时候到这里：日志出现 `[warn] 上一场 … 被看门狗强杀`、`report.json` 里出现 `wedge_ledger`
> 或 `browser_exit`、或要判读会话目录里那三份证据。**正常会话没被杀就不必读这本。**
> 执行主干在 `docs/agents/apply-runbook.md`（步骤 1-6），节奏与额度开关在
> `docs/agents/apply-tuning.md`。术语约定：代码与文件名用 `wedge`，中文一律写「卡死」。

## 止损与取证开关（进程外看门狗 / 取栈 / 出网探针 / 跳岗台账）
默认值与阈值的真源是 `scripts/_forensics.py` 与 `scripts/_selfguard.py` 里的常量，加上
`_limits.py` 的「布尔 env 开关」小节（几个开关的取值表**刻意不同**）。下面写的是**读法与代价**，
不是数值的副本——要确认某个默认值，读那两个文件的常量定义，别信任何一处转述。

- `LIVE_PREFLIGHT_WATCHDOG`（默认 180 秒，0 = off）—— 起飞前自检的进程外守卫：自检段卡在协议
  调用上就整树 SIGKILL，**动手前同样落 `WATCHDOG_KILLED.json`**（2026-10-07 补的口：此前这条看门狗
  杀完只留一份栈，marker 与网络读数两格全空，判读只能靠人事后手动探测）。相位取值见下面「卡死取证
  怎么读」。防的是 `20260925-215522` 那一类形态。
  **卡死（代码与文件名叫 wedge）是什么**：进程还活着，却停在一次永不回话的协议调用上，自己醒
  不过来，只能由进程外的看门狗杀掉——与「慢」是两回事，慢会继续拍心跳。
  - 自检本体（`LIVE_PREFLIGHT`，默认开；关闭认哪些值见 `_limits.py` 的布尔 env 小节）2026-10-09 起
    点的是列表里**第一张可见**的卡片（判据 `is_visible()`，与投递路径同一条），不再是「第一个 DOM
    命中」——会话 `20261009-092824` 就是被一个隐藏节点骗掉整场：四步全抛 `Element is not visible`、
    不开跑、零投递、`shots/` 一张图都没有。日志现在同时打「候选 N 个 / 可见 M 个」，于是
    **「一个都没找到」与「找到了但全不可见」分得开**；两种形态的后果照旧不同——候选 0 跳过自检、
    由中途熔断兜底；全不可见仍判**不开跑**并落 `preflight_click_failed`，且当场补一张
    `*_preflight-click-failed.png` 存证（存证自身失败只 warn，不改变判定）。
- `LIVE_WATCHDOG`（默认 240 秒，0 = off）—— **会话中途**的停摆阈值。主线程每走一个机械节点拍
  一次心跳（截图 / 滚动轮 / 岗头 / 等回复轮询 / 限速与长休息的分段 / 搜索与推荐的等首批 XHR /
  followup 入口），心跳停摆超阈值且进程还活着即整树止损，并往会话目录落
  `WATCHDOG_KILLED.json`（这份形状两代共用，见下面「哪一条看门狗掐的」），下一场开跑自动呈报。
  - 建议不低于 120 秒（合法无心跳上界 = `_limits.PACE_BEAT_INTERVAL`，现 30 秒，120 = 4 倍余量）。
    ⚠️ **代码不拦小值**（收任意非负整数），护栏用例只锁默认 240 与 30 的关系 —— 调小这一步
    没有机器兜着，先确认新纳入的长等待都有拍点再调（#58 的教训：长休息 8-25 分钟与晚间限速
    曾经不拍心跳，240 秒的阈值会把健康会话整树杀掉，还会把**已经投出的岗**回灌成卡死岗）。
  - 取证里 `stale_seconds = -1` 表示心跳文件消失（按永久停摆处置），不是「停了 1 秒」。
- `LIVE_WEDGE_DUMP`（默认开，关只认 `0` / `off`）—— 卡死现场取栈。每个心跳节拍重武装
  `faulthandler`，无心跳满 90 秒把全线程栈写进会话目录 `wedge-stack.txt`。
  **该文件为空 = 本场没卡死**；非空先辨真伪：栈顶停在 `time.sleep` / `wait_for_timeout` 且落在
  限速或采集等待里 ⇒ 那是取证缺陷不是卡死（#58 修前实测三份都这样），按缺陷报告。武装或落盘
  失败只 warn，取证层绝不反噬投递。
- `LIVE_NET_PROBE`（默认开，关只认 `0` / `off`）—— 看门狗判定要杀之后、动手之前自己打一次
  DNS + TCP + **一次真实 HTTPS 往返**（阶梯与判读表都在下面「卡死取证怎么读」，那里是唯一一份），
  结果写进 `WATCHDOG_KILLED.json` 的 `net_probe`。代价：已经判定要杀的那一场多花两段超时之和
  （TCP 段与 HTTP 段各一个上界，数值真源是 `_forensics` 的 `NET_PROBE_*` 常量，别在这里抄）；
  健康会话一次都探不到。它是三个嫌疑里「这台机器此刻不通」的唯一正面读数。
- `LIVE_WEDGE_SKIP`（默认开，关只认 `0` / `off`）—— 卡死岗跳岗台账的临时放行开关，机制见下面
  「跳岗台账」条。
## 卡死止损、读法与跳岗台账

- **会话中途卡死止损（LIVE_WATCHDOG，2026-09-27）**：看门狗检测到心跳停摆即整树强杀——
  agent 遇 `[warn] 上一场 … 被看门狗强杀` 呈报时同样**只报事实**（取证 JSON 的停摆时长
  / 最后节点 label / 岗位名与 eid），根因定性归用户；被杀会话无 report.json（零投递零台账），
  重启本身不构成风控信号。**卡死取证怎么读（#56，2026-09-28）**：被杀会话目录里
  `wedge-stack.txt` 为空＝本场没卡过，非空＝卡死时的全线程栈。**调用点认 label、不认栈**：2026-09-29
  两份真栈实测，faulthandler 只打得出 OS 线程，而业务调用帧跑在 greenlet 里、栈里根本不现身，
  栈顶恒为 `selectors.select`——栈只回答「在等驱动回话」还是「在算」，「停在哪个无超时调用上」
  由 `heartbeat.json` 的细颗粒 label
  （`click:bounding-box:pre` / `jd:dom-poll:3:post` / `pace:break` / `search:wait-xhr:12` /
  `*:error` 一族）回答，label 落在 `pace:*`／`wait-xhr` 一族时是合法等待、不当卡死证据（#58）；
  `WATCHDOG_KILLED.json` 的 `in_job` + `last_eid` 回答「死在哪个岗上」。**哪一条看门狗掐的**看同一份
  marker 的 `watchdog_phase`（`preflight` / `session`）：两代在 preflight 段**并存**（`_preflight_guarded`
  连心跳版也武装），**先到期者留证**，所以相位只回答「谁动的刀」，停摆时长一律看 `stale_seconds`；
  两条判据各占一键——时限那条写 `timeout_seconds`、停摆阈值那条写 `stall_seconds`，另一代的那个键恒
  `null`（把两种语义塞进一个键，判读就得先猜）。旧 marker 没有相位这一格 ⇒ 呈报不点相位，别替它猜一个。
  呈报行 `[warn] 上一场 …` 据此点明「起飞前自检段击杀」或「会话中途击杀」——两段往下的追查路线不同
  （起飞前那次点击卡住＝浏览器/驱动起得来吗；会话中途卡住＝具体岗位与端点）。**栈拍不到 greenlet，所以
  另加两把尺（#56 取证 A/B，2026-10-05）**：① `heartbeat.json` 末三键 `handlers_live`（当时还挂着
  几个 response 处理器）/ `handlers_inflight`（有没有我方处理器正停在「取响应体」那次往返上）/
  `handler_last_frag`（最后进入的是哪个端点），三键同时镜像进 `WATCHDOG_KILLED.json`——处理器跑在
  greenlet 上、**不出现在线程栈里**，这三项是「嫌疑①＝我方往返挂住」唯一的正面读数；配套的
  `handler:<端点尾段>:enter` / `:exit` 两拍由处理器自己写，enter 那一拍落在**挂住之前**，所以
  `inflight=1` 来得及落盘（只在正常节拍里读计数会永远读到 0，等于反着写）。读法注意：收尾采集
  之后 `handlers_live` 天然偏高 1（聊天页那个处理器没有注销点，不是泄漏）。② `WATCHDOG_KILLED.json`
  的 `net_probe` 三段各答一层：`dns_ok` 解析、`tcp_ok` 能不能握手、`http_ok` 拿不拿得到响应状态码
  （配 `http_status` / `http_total_ms`）——**嫌疑③＝这台机器此刻不通**的正面读数就是它，而判读
  按 `http_ok`、不按 `tcp_ok`（2026-10-09 纠正）：**`tcp_ok=true` 而 `http_ok=false` ＝连上了对端
  （本机就是那个本地代理）却取不回内容＝嫌疑③ 的正面证据**。那场缺的正是这一格：会话
  `20261009-093228` 于 09:41:31 被击杀，取证里 `tcp_ok=true`、解析地址 `198.18.0.116`，而**同一刻
  同一台机器**人工复测 `urlopen` = **HTTP 200 / 538056 字节 / 630ms**；旧探针根本没问过「这一刻取不
  取到站点内容」，按旧表只能把那场读成「三嫌疑都无正面证据」。`resolved_via_proxy_fake_ip` 也**不是**
  故障证据，它回答的是「这条读数走的哪条路」：这台机器的系统代理（`127.0.0.1:7890`）是 fake-IP 模式，
  命中 198.18/19 段＝代理正在管这条路（正常工作态），不命中才是直连公网。读数细节：TCP 不通时 HTTP 段
  不跑，那三键恒在（`false` / `null` / `0`），插页那族四键同样恒在（`blocked_shape=false`、`probe_path`＝
  本次**意图**的 path（那一趟并没真发出去）、`http_location` / `http_content_encoding`＝`null`）；**任何已收到的状态码都算 `http_ok=true`**（含 4xx/5xx——
  这族键答「路通不通」，不答「页面好不好」）；`http_ok=true` 而 `error` 非空＝状态码已到手但读体被截断，
  两个读数并存、别互相吃掉。**四格判读**（inflight × `net_probe.http_ok`）：inflight≥1 + 探针失败
  ⇒ ①③都有正面证据，先查代理/出网；inflight≥1 + 探针成功 ⇒ ①成立（但**探针成功不排除③**——看门狗
  探的是它自己视角，浏览器可能走另一条路；这条限制既加不了也减不掉）；inflight=0 + 探针失败
  ⇒ 我方处理器清白，指向③或②；inflight=0 + 探针成功 ⇒ 三嫌疑都无正面证据 ⇒ 指向②（网站/浏览器
  把渲染端占死），并把本场当作「新增取证没起作用」的读数一并呈报——**但最后这一格 2026-10-15 之后要加
  一条前置**：先读 `blocked_shape`，它为 `true` 时③已经有正面证据（请求被引导进认证/安全流程），
  「三嫌疑都无正面证据」这句话本身就不成立，不许跳过那一格直接落到②。**2026-10-11 那场把这张表用错了一次**：`http_ok=true` 被读成「③已排除」——可探针当时打的是**首页**，首页常年回 302，那一格答的是「这条路通不通」，答不出「正卡住的那个端点给不给内容」。取证因此多一族键（键名都在 `_forensics`）：`probe_path`＝本次探测的 path（会话卡在详情往返上就探同形状的 `/job_detail/{eid}.html`，eid 取自**同一份心跳**、不开第二份真相；缺 eid 回落 `/`；TCP 都没通时它是**意图值**，别读成「真发出去过」）；`http_location` / `http_content_encoding`＝响应的两个头；`blocked_shape`＝插页形态，**两条通道任一命中即真**——① body 命中文案特征（`安全验证` / `完成验证后即可正常使用` / `verify.html` / `请稍候`），② 3xx 且 `Location` 命中认证/安全流程（`/web/passport/zp/`、`security.html`、`verify.html`）。**通道②是主通道，不是补充**：2026-10-15 用生产探针自己的形状（`http.client`、无 cookie、非浏览器 UA、不跟跳转）实测那条详情页，拿到的是 `302` + `Location: /web/passport/zp/security.html…` + `Content-Length: 0`，**body 是空的**——只读 body 的第一版判据在它自己的 motivating 现场上答 False，这一族键差点白加。⇒ 判读顺序：`http_ok=true` 而 `blocked_shape=true` ＝路通、取回的是插页＝**③的正面证据**，那一场的「三嫌疑都无正面证据」不成立；反过来 `blocked_shape=false` 只等于「没检出特征」，**两条已知够不着的地方**都要写在读数旁边：`http.client` 不解压（`http_content_encoding` 非空时 body 判据没有发言权）、探针本身匿名且非浏览器 UA（站点给插页本就是正常 bot 检测，所以这一格**分不清**「这个出口被风控」与「匿名本来就不给看正文」，不许据此判定 IP 被封）。两条通道都**只认命中**，谁也不许反着读成「取到了岗位内容」；三格与 `http_ok` 并存，互不吃掉。**`None` ≠ `0`**：三键或整个
  `net_probe` 是 `null` 说明那一场早于取证 A/B、或开关被关过，不许读成「读数为零」——而 `net_probe`
  里面的 `http_status=null` 是另一回事，那是「探了、没拿到状态码」。三份证据连同截图呈给
  用户后再谈原因（#56 C 段是 HITL——证据到手前不写结论）。**跳岗台账（#56 B1 + #58 守卫）**：
  带 `in_job`+eid 的卡死岗会被下一场开跑回灌进 `private/data/[<profile>.]wedge_skipped.json`
  并从此不投（搜索/推荐/补投/浏览噪声全绕开，代价＝可能漏投一个达标岗）；但**已出现在
  `applied_history` 里的岗不入账**（呈报点名并要求核查，计数落 `wedge_ledger.already_applied`）
  ——成功投出的岗被击杀记到头上属归因可疑，不构成「这个岗会卡死」的证据；开跑呈报里能看到
  台账清单，临时放行用 `LIVE_WEDGE_SKIP=off`（放行期间也不回灌）。
